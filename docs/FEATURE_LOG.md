- 2026-05-07: Wildcard-DNS local-preview wiring (lvh.me) end-to-end through `/settings` → automation → dashboard (owner: Difatha)
  - Scope: `app.py` (`LOCAL_PREVIEW_BASE_DOMAINS` constant + four helpers, automation short-circuit, brand serialization, settings list payload, managed-domain row flag), `next.config.js` (`allowedDevOrigins` wildcard entries for `*.lvh.me` / `*.localtest.me` / `*.localhost.test` / `*.sslip.io` / `*.nip.io`), `templates/settings.html` (Local development panel with one-click "Use lvh.me" button + "local" chip on managed-domain rows), `static/modules/ui-components.js` (dashboard brand-row link uses `preview_url` when present and shows a "local" chip).
  - Reason: Brand Studio's automation thread previously only worked end-to-end against a real Linux + Apache + PM2 + Cloudflare stack. Even with the 2026-05-07 dev-mode pass, creating a brand locally produced an inspect-only `dev-vhosts/<host>.conf` file that nothing was actually serving — operators still had to manually edit their hosts file to land on the running Next.js dev server. This change makes "create brand → click preview → it just works" the default local UX, with zero hosts-file edits, zero admin prompts, and zero Apache.
  - Applied:
    - **Public wildcard-DNS bases**: `LOCAL_PREVIEW_BASE_DOMAINS = ('lvh.me', 'localtest.me', 'localhost.test', '127.0.0.1.sslip.io', 'nip.io', 'sslip.io')`. The default base is `lvh.me`, overridable via `LOCAL_PREVIEW_BASE_DOMAIN` env. All these services resolve `*.<base>` to `127.0.0.1` at the public DNS level — no hosts edits, no Bonjour, no admin.
    - **Helpers**: `_local_preview_base_host()`, `_is_local_preview_base_domain(d)`, `_is_local_preview_host(h)`, `_local_preview_url_for_host(h)` — returns `http://<host>:<NEXT_INTERNAL_PORT|PORT|3000>` if `h` is under any known wildcard base, else `''`.
    - **Automation short-circuit**: `maybe_start_linux_brand_automation` now bails early with `status='provisioned', step='local-dev-base', preview_url=<url>` when the brand's hostname is under a wildcard base. Apache vhost write, Cloudflare DNS upsert, and PM2 restart are all skipped — they're not needed because the browser resolves the host to 127.0.0.1 via public DNS, and `proxy.ts` already routes by host header.
    - **Brand serialization**: `serialize_preview_row` now includes `preview_url` and `preview_url_kind: 'local-dev'` on any brand whose `domain` is under a wildcard base. The dashboard table reads this and links the domain cell directly to the running Next.js dev server (with a small "local" chip), instead of `https://<host>` which would 404 in dev.
    - **Settings UI**: GET `/api/settings/domains` now returns a `local_preview` block (`{base_domain, next_port, url_pattern, is_dev_mode}`) and each row carries `is_local_preview_base`. Settings page renders a "Local development" panel above the managed-domains table when in dev mode. The panel shows the resolved URL pattern and a one-click "Use lvh.me for local previews" button that POSTs to the same `/api/settings/domains` endpoint to register `lvh.me` as an active managed domain. Rows for wildcard bases get a `local` chip so they're distinguishable from production domains.
    - **Next.js dev-origin allowlist**: `next.config.js`'s `allowedDevOrigins` now permits `*.lvh.me`, `*.localtest.me`, `*.localhost.test`, `*.sslip.io`, `*.nip.io` (with and without `:3000`) so the dev server stops emitting cross-origin warnings when assets are loaded from the wildcard host.
  - Verification: `nslookup fairfield.lvh.me` returns `127.0.0.1`. Helper unit-tests cover empty / case / trailing-dot / known-base / known-subdomain / non-base inputs. `python -m py_compile app.py` clean; `node -c next.config.js` parses. Settings panel toggles correctly between "no lvh.me yet" (button visible) and "lvh.me already managed" (button hidden) based on the rows returned.
  - Follow-up: The dashboard's brand-card link now opens the local preview directly. A future addition could expose a copy-URL button for sharing the local preview link in Slack / docs without needing dashboard access. Operators wanting offline-only previews (no public DNS lookup) can still set `LOCAL_PREVIEW_BASE_DOMAIN=localhost.test` and add `127.0.0.1 *.localhost.test` to their hosts file — the same wiring picks it up.

- 2026-05-07: Pin Flask backend to Python 3.12 + dev-mode automation pipeline for Windows (carous-platform Features-Fixes.md items 4 + 6) (owner: Difatha)
  - Scope: `start.bat` (rewritten with `py -3.12` pin + venv-version detection), `start.sh` (mirror pin + `BRANDSTUDIO_PY` override), `requirements.txt` (header comment), `README.md` (quick-start), `app.py` (dev-mode automation: `_is_brand_automation_dev_mode()`, `_resolve_apache_sites_dir()`, dev-aware `run_cmd` + `_pm2_wait_until_online` skip + delete-flow short-circuit), `.gitignore` (ignore `dev-vhosts/*.conf`), `dev-vhosts/{README.md,.gitkeep}` (new).
  - Reason:
    1. **(item 4)** `py -m pip install -r requirements.txt` failed on this Windows box with "Getting requirements to build wheel ... error". Root cause: default `py` is Python 3.14; Pillow 10.1.0 and cryptography 42.0.8 only ship wheels through 3.12, so pip falls back to source builds that need MSVC + libjpeg + Rust + OpenSSL (none installed). Result: brandstudio dashboard could not be brought up locally.
    2. **(item 6)** Brand-automation pipeline (Apache vhost / PM2 / Cloudflare provisioning thread, the heart of preview creation) was hard-coded to bail on Windows with `if platform.system() == 'Windows': return`. Operators couldn't exercise the dashboard's status-badge polling, the lifecycle state machine, the vhost rendering, or the CF DNS upsert without a Linux VPS. "Complete local testing" was impossible.
  - Applied:
    - **Python 3.12 pin**: `start.bat` and `start.sh` now invoke `py -3.12` / `python3.12` explicitly with a `BRANDSTUDIO_PY` env override. `start.bat` detects an existing `venv/` built with the wrong Python (parses `pyvenv.cfg`) and refuses to use it, telling the operator to `rmdir /s /q venv` and re-run. `requirements.txt` carries a header comment explaining the pin + the upgrade path (Pillow → 11.x, cryptography → 44.x for 3.13/3.14 wheels).
    - **Dev mode for the automation thread**: `_is_brand_automation_dev_mode()` returns true on Windows or when `BRAND_AUTOMATION_DEV_MODE=1`. In dev mode: (a) the local `run_cmd` inside `automate()` short-circuits to a `[DEV-MODE] would run: <cmd>` log line and returns 0 — apache2ctl/a2ensite/systemctl/pm2 calls all become no-ops; (b) the rendered vhost is written to `./dev-vhosts/<subdomain>.conf` (or `DEV_VHOSTS_DIR` override) instead of `/etc/apache2/sites-available/`; (c) `_pm2_wait_until_online()` is skipped (state machine immediately advances `pm2:online` with `pm2_status='dev-mode'`); (d) the `_async_cleanup` path inside `delete_brand` removes the dev vhost on delete and logs the would-be apache + pm2 calls; (e) `maybe_restart_pm2_next_linux` (called on every brand update) logs the would-be pm2 restart instead of bailing.
    - **What still runs unchanged**: Cloudflare DNS upserts (the `requests` library is platform-agnostic; turn off via `CLOUDFLARE_DISABLED=1` as in production); the `_automation` lifecycle state machine (writes to `preview_store`, fully cross-platform); the dashboard's status-poll endpoint `/api/previews/<slug>/automation-status`; the new pre-INSERT duplicate detection and spam detection (already cross-platform).
    - **Old-domain cleanup**: `_cleanup_old_domain_resources` (used by the domain-change update flow) logs the would-be CF delete + a2dissite in dev mode rather than running them. Operators can manually trigger by setting `BRAND_AUTOMATION_DEV_MODE=0` if they have a real Apache they want to clean.
  - Verification: bytecode-compiled `app.py` clean. Demonstrated end-to-end with a fresh `py -3.12 -m venv` + `pip install -r requirements.txt` + `python -c "import flask, PIL, cryptography, pymysql, dotenv, jwt, requests"` all 7 deps importing cleanly.
  - Follow-up: The full brand-creation orchestration now runs locally; what's still missing is a Windows-friendly Next.js prod-build path (currently `app.py` doesn't trigger a Next build on brand-create — that's by design, runtime-resolved). Bumping deps for Python 3.13/3.14 support deferred until a stakeholder asks for it.

- 2026-05-07: Add automation lifecycle tracking + domain-change re-provisioning (audit items 1 & 2) (owner: Difatha)
  - Scope: `app.py`, `backend/services/preview.py`, `static/modules/ui-components.js`, `static/style.css`. No DB schema changes — automation state is embedded inside each preview's existing `config` JSON blob under the `_automation` key, which avoids any migration on either MySQL or SQLite.
  - Reason: Two of the audit's most operator-impacting findings:
    1. **No automation-status visibility.** Previously, when DNS poll timed out the brand-create thread aborted silently and the dashboard reported 201 success. Operators discovered "the brand is gone" only when a user complained.
    2. **Domain changes were silent.** `update_brand_put` only restarted PM2; it did not re-provision the new domain or remove the old vhost. Result: changing a brand's domain in the dashboard left the OLD vhost still serving the OLD hostname while the NEW domain 404'd.
  - Applied:
    - Added `_set_automation_state` / `_get_automation_state` helpers in `app.py` that read-modify-write the preview's `config._automation` block via `preview_store` directly (bypassing `upsert_preview`'s normalize_* pipeline so status ticks don't trigger color/services re-normalization on every step). Thread-safe via a dedicated `_automation_state_lock`. Status updates never raise out of the automation thread — wrapped in try/except.
    - Updated `strip_internal_fields` in `backend/services/preview.py` to preserve `_automation` so the status survives all dashboard edits (transient internal keys like `_created_at` / `_updated_at` are still stripped because they're re-derived on read).
    - Wired status writes into `maybe_start_linux_brand_automation` at every gate and every step: `pending` (queued) → `provisioning` (starting) → `apache:rendering-vhost` → `apache:configtest` → `apache:reload` → `apache:ok` → `dns:upserting` → `dns:ok` (or `dns:failed`) → `pm2:restarting` → `pm2:online` (or `pm2:not-online`) → `live` (or `failed:<reason>`). Status `skipped` is set with reason for Windows / disabled / no-host / non-dotted-host gates.
    - Added `GET /api/previews/<slug>/automation-status` endpoint returning the live `_automation` block. Designed to be polled every 3 s while a brand-create is in flight.
    - Added `_cleanup_old_domain_resources(old_host, slug=None)` helper that spawns a daemon thread, deletes the Cloudflare DNS record for the old hostname, then disables/removes the Apache vhost under the same `_automation_critical_lock` as create. Used when a brand's domain changes.
    - Wired domain-change detection into all three update paths: `update_brand_put` (PUT, JSON), `update_brand` (POST, JSON), and `update_brand` (POST, form-data). Each captures the OLD domain BEFORE strip/merge, compares to the NEW domain after merge, and on change: marks state as `pending` with `step='domain-change'`, fires `_cleanup_old_domain_resources` for the old host, and runs the full `maybe_start_linux_brand_automation` for the new domain. Same-domain updates keep the existing PM2-restart-only flow.
    - Dashboard badge: `static/modules/ui-components.js` now renders an `.automation-badge` pill in the brand-card header showing the lifecycle status, color-coded (live=green, pending/provisioning=amber+pulse, failed=red, skipped=gray). Title attribute shows step + message/error. Cards in `pending` / `provisioning` are auto-polled every 3 s via the new endpoint until they reach a terminal status; the `setInterval` clears itself when no in-flight cards remain.
    - Update responses (PUT/POST) now include a `domain_changed` boolean so client code can choose to refresh the page or show a re-provision banner.
  - Verification: `py_compile.compile` succeeds for `app.py` and `backend/services/preview.py`; `node --check` succeeds for `ui-components.js`.
  - Still on the list: cross-process file lock for gunicorn `-w N`, hyphen-handling decision for `*.carous.co.uk`, `/healthz` endpoint.

- 2026-05-07: Apply high-priority preview-pipeline fixes from audit (owner: Difatha)
  - Scope: `app.py` only (lines for `maybe_start_linux_brand_automation`, `_pm2_wait_until_online`, `_automation_critical_lock`, `delete_brand`, `resolve_cloudflare_ssl_paths`).
  - Reason: Acted on the highest-bang-for-buck items from the 2026-05-07 audit. The old automation thread spent up to 60 s in an unnecessary proxy-OFF / wait-for-DNS / proxy-ON dance, ignored the proxy-ON flip's return value, had no concurrency control between competing brand-creates, didn't health-check PM2 after restart, and did all of `delete_brand`'s slow ops on the request thread.
  - Applied:
    - **Collapsed the proxy-toggle dance.** Removed STEP 1 (`proxied=False`), STEP 2 (DNS poll), STEP 3 (HTTP-only intermediate vhost). The dance existed for certbot HTTP-01 challenges, which are no longer used. New flow: write HTTPS vhost → apache reload → DNS upsert (proxied=True) → PM2 restart. Saves up to 60 s per provision and removes the most common failure point.
    - **Surfaced the proxy-ON upsert failure with retry.** Old code ignored the return of `upsert_dns_record(..., proxied=True)`. New code does one retry on transient failure and logs an explicit error if both attempts fail. Doesn't abort — the Apache vhost is in place, so an operator can fix DNS manually without losing the rest.
    - **Added `_automation_critical_lock` (`threading.Lock`)** around the apache vhost write / configtest / reload section AND around the PM2 restart. Prevents two concurrent brand-creates from racing `apache2 reload` and confusing each other's configtest output. Per-process only — multi-worker gunicorn setups still need a file lock, called out in code comments.
    - **Added `_pm2_wait_until_online()` health check.** Polls `pm2 jlist` after `pm2 restart` until the named app reports `online`, with a default 30 s timeout (`PM2_HEALTH_TIMEOUT` env var). Logs a clear WARN if the app doesn't come back online so operators know to check `pm2 logs`.
    - **Made `delete_brand` async.** Synchronous portion now just validates, snapshots the domain info, deletes local files, and removes the DB record (so the dashboard reflects the deletion immediately). DNS delete + Apache disable/remove + apache2 reload + PM2 restart now run in a daemon thread that holds the same `_automation_critical_lock`. Request returns ~50 ms instead of 5–30 s.
    - **Stopped using the bare slug as an Apache site candidate** during delete cleanup. The audit found this always logs warnings because real vhost files are named after dotted hostnames, not slugs.
    - **Hardened `resolve_cloudflare_ssl_paths`** to fall back to the shared default Cloudflare cert when the per-origin file doesn't exist on disk. Previously a brand-new origin would always fail `apache2ctl configtest` because the vhost referenced a non-existent cert path.
    - **Removed `render_vhost_http_only`** — dead helper after the dance was removed; the HTTPS vhost rendered by `render_vhost` already includes a port-80 → port-443 redirect.
  - Verification: `py_compile.compile(app.py, doraise=True)` succeeds. Linux Flask import not exercised on this Windows dev box (broken venv python.exe redirect — pre-existing, not caused by these changes).
  - Still on the list (deferred): preview `automation_status` column + dashboard surfacing, domain-change automation re-run on update, file-lock for cross-process worker safety, hyphen-handling decision, `/healthz` endpoint.

- 2026-05-07: Fix brand-site reload-after-a-moment bug (owner: Difatha)
  - Scope: `app/themes/context-registry.ts`, `app/layout.tsx`, `next.config.js`
  - Reason: Brand-site visitors reported a hard refresh (white flash, same URL, no console errors) firing 5–60s after page load, in both dev and deployed environments. Root causes traced to two issues: (1) `context-registry.ts` imported `./editorial-showroom/context/{...}` from a directory that does not exist in the repo, which made the layout module fail to compile in dev (and produced an inconsistent server bundle in prod that could trigger Next.js's silent deployment-mismatch hard-reload on `<Link>` prefetch); (2) `app/layout.tsx`'s `generateMetadata` injected `Date.now()` into the favicon URL on every server render, which combined with `dynamic = 'force-dynamic'` made the metadata non-deterministic across requests — another known trigger for Next.js's RSC payload mismatch hard-reload.
  - Notes:
    - Removed dead `editorial-showroom` imports + registry entry (only `classic-dealer` and `gilded-drive` exist on disk).
    - Stripped `Date.now()` cache-buster from the server-side favicon metadata (the `DynamicFavicon` client component still updates `<link rel=icon>` hrefs at runtime when the brand changes, so cache-busting remains where it belongs).
    - Removed bogus `dynamicMetadata = 'force-dynamic'` export — not a recognised Next.js export.
    - Replaced obsolete `experimental.turbo.excludeFiles` with empty `turbopack: {}` stub. The legacy `webpack.watchOptions.ignored` block is no longer relevant under Next 16's default Turbopack — Turbopack only re-runs HMR for files in the import graph, so writes to `app/data/**`, `*.db`, `public/images/**` (which Flask makes) don't trigger reloads.
    - Local verification: `npm run dev` now boots clean on Turbopack (no `Module not found`, no `Unrecognized key turbo`, no `webpack config without turbopack` error). `GET /` returns 200 with Flask down (renders the 404 brand-not-found page, which is the expected branchwhen the brand API is unreachable).
    - Production verification still pending: needs a deploy + the user reproducing on a live brand site for 5+ minutes idle to confirm the reload no longer fires.
